## Executive Summary

The architecture is sound. Three-layer design (content script + main-world script + background service worker) covers the URL paths a tracking-strip extension needs to cover: DOM `<a href>`, `MutationObserver` for SPA-injected links, and main-world monkey-patches of `history.pushState` / `replaceState` / `window.open`. TypeScript strict, modern tooling (WXT/Vite), cross-browser (Chrome MV3 + Firefox MV2), no external network calls (good for a privacy tool). Code is clean and reads well.

The notable issues are: (1) a real correctness bug — the main-world rewriter and the content-script rewriter use *different* logic, so programmatic navigation gets different treatment than link clicks; (2) a storage migration gap — new default params won't reach existing users; (3) a MutationObserver scheduling redundancy; plus the usual repo-plumbing gaps for a brand-new project.

## 🟠 High

### H1. Two-rewriter logic divergence

`utils/rewriter.ts:30-52` (used by content script) and `entrypoints/main-world.ts:29-46` (used to intercept programmatic navigation) implement URL rewriting with different rules.

**Content-script rewriter** (`utils/rewriter.ts`) honors:
- `_custom` flag — per-param override only kicks in when explicitly set by user
- `globalMode` — falls back to global `remove` vs `rewrite` setting
- `globalRewriteValue` — used when no per-param value is set

**Main-world rewriter** (`main-world.ts`) only checks:
- `rule.action === 'rewrite' && rule.value !== undefined` → uses `rule.value` directly
- Otherwise removes the param

So a default `utm_source` config of `{ action: 'remove' }` (no `_custom`, no value):
- Content-script path: globalMode=`rewrite` + globalRewriteValue=`donttrackme` → param becomes `utm_source=donttrackme` ✓
- Main-world path: `rule.action === 'rewrite'` is false → param is removed ✗

**This means clicking a link rewrites `utm_source` to `donttrackme`, but a `history.pushState` with `utm_source` strips it entirely.** Inconsistent observable behavior.

**Fix (applied):** main-world.ts imports the shared `rewriteUrl` from `utils/rewriter.ts` and uses it. WXT bundles each entrypoint independently, so the import is fine — the type-only import for `ExtensionConfig` is already present.

### H2. `getConfig()` shallow-merge drops new default params on upgrade

`utils/storage.ts:43-54`:

```typescript
return {
  ...DEFAULT_CONFIG,
  ...stored.config,   // ← spreads top-level fields including .params, replacing defaults
};
```

When a new release adds default tracking params (e.g., a new `vero_id` for Vero email tracking, or `twclid` for Twitter), existing users won't see them — `stored.config.params` overwrites `DEFAULT_CONFIG.params` wholesale. Param-set updates require user-initiated "Reset to defaults", which also wipes their customizations.

**Fix (applied):** deep-merge the `params` field specifically:

```typescript
return {
  ...DEFAULT_CONFIG,
  ...stored.config,
  params: { ...DEFAULT_PARAMS, ...stored.config.params },
};
```

**Trade-off acknowledged:** if a user explicitly *deleted* a default param via the popup, it will reappear on upgrade. That's worse than the alternative (everyone-on-old-version misses new tracker params forever). For users who delete a default — they'll see it once, can re-delete. Documented in the new CHANGELOG entry.

A more elaborate solution (track deletions in a `deletedDefaults: string[]` field) is overkill for v1.

## 🟡 Medium

### M1. Redundant `scheduleScan()` after MutationObserver inline processing

`entrypoints/content.ts:64-81` — the observer callback inline-processes all newly added anchor nodes, then calls `scheduleScan()` which queues a `requestIdleCallback` to re-scan **every** link on the page. The full re-scan is redundant for the inline-processed nodes.

The likely reason `scheduleScan` exists: catching `href` *attribute mutations* on existing nodes (the current observer only watches `childList`, not attribute changes).

**Fix (applied):** add `attributeFilter: ['href']` to the observer's options, handle attribute mutations inline, drop `scheduleScan()` from the observer callback. Keep `scheduleScan()` as the cleanup target if the loop somehow gets behind, but don't call it on every mutation.

This eliminates a 350ms-cadence full-document re-scan that was firing on every SPA mutation.

### M2. README install instructions have placeholder URL

`README.md:67`:
```
git clone https://github.com/YOUR_USERNAME/link-scrubber.git
```

**Fix (applied):** updated to `Avicennasis/link-scrubber` once the repo exists.

### M3. `scripting` permission may be unused

`wxt.config.ts:7` requests `permissions: ['storage', 'scripting', 'activeTab', 'tabs']`. The code uses `web_accessible_resources` to inject the main-world script (loaded via `<script src=>` in content.ts), not `chrome.scripting.executeScript`. The `scripting` permission may be dead weight — but WXT's MV2/MV3 bridging may add it implicitly for Firefox compatibility. Safer to leave it for now; verify later by attempting to drop it and running `wxt build` for both targets.

**Decision:** leave as-is for v1, flag for follow-up after a build-without-it experiment.

### M4. No tests

The pure rewriter (`utils/rewriter.ts`) has many testable cases:
- default param + globalMode=rewrite → rewrites
- default param + globalMode=remove → removes
- `_custom: true` per-param override
- multiple values for same key
- `javascript:` / `mailto:` skip
- malformed URL skip
- unknown param skip

**Fix (applied):** added `tests/rewriter.test.ts` with vitest. Network-free, runs in node. Includes a happy-path matrix covering the two-rewriter parity (since both paths now route through the same function).

### M5. No LICENSE file

README says "MIT" but there's no `LICENSE` file. Some package registries (npm, AMO, Chrome Web Store) and license-scanners look for the file specifically.

**Fix (applied):** added `LICENSE` (MIT, copyright Avicennasis 2026).

### M6. No CHANGELOG

Single-commit "Initial release" — no record going forward of what changed across versions. v1.1.0 will need it.

**Fix (applied):** added `CHANGELOG.md` with v1.0.0 entry + v1.1.0 entry covering this review's fixes.

### M7. Storage-change broadcast triggers full re-scan on every config write

`background.ts:31-39` — `storage.onChanged` listener broadcasts `configUpdated` to every tab on every storage write, including writes from the popup (e.g., toggling a single param). Each receiving tab calls `scanAllLinks()` which re-scans the entire page.

For a popup with rapid toggling (user adjusting per-param actions), this means every click triggers a full-document re-scan in every open tab. Not wrong, just expensive.

**Fix (deferred to v1.2):** debounce the broadcast in background, or have the content script debounce the re-scan. Flagged in CHANGELOG as a known performance characteristic. Noted, not blocking.

## 🟢 Low (left as-is unless noted)

### L1. Param-order changes after rewrite

`url.searchParams.delete(key)` followed by `url.searchParams.append(key, ...)` moves the rewritten key to the end of the query string. Original `?a=1&utm_source=fb&b=2` becomes `?a=1&b=2&utm_source=donttrackme`. Most servers don't care; some signed/deep-link URLs do. Edge case — leaving as-is.

### L2. `<base href>` resolution in main-world rewriter

`new URL(urlString, document.baseURI)` resolves relative URLs against the page's `<base href>`. A page that sets a tracker-friendly base would be re-canonicalized through the tracker. Pretty edge-case — leaving.

### L3. `activeTab` + `<all_urls>` host_permissions are slightly redundant

`<all_urls>` already grants the access `activeTab` would scope. WXT may still want both for cross-browser quirks. Leaving.

### L4. `_custom` sentinel could be a separate `customActions` map

Current schema:
```ts
params: Record<string, { action: 'remove' | 'rewrite', value?: string, _custom?: boolean }>
```

A cleaner shape might be:
```ts
defaults: string[]                        // known param names
customActions: Record<string, ParamConfig> // explicit user overrides
```

But the current shape works and migrating storage formats is non-trivial. Leaving.

### L5. No debounce on storage-change broadcast (see M7 — same root)

### L6. Popup `reload()` re-fetches everything on every action

Every click in the popup calls `reload()` which fetches stats, fetches config, re-renders all params. Cheap, but inefficient. Leaving.

## What's good (worth keeping)

- **Three-layer rewriting** (content + main-world + background) covers all the common navigation paths. This is the right architecture.
- **No external network calls.** Audit-friendly for a privacy extension. Verified by grep — `fetch`, `XMLHttpRequest`, `navigator.sendBeacon`, `WebSocket` not present anywhere.
- **MutationObserver for SPAs.** The inline processing of added anchor nodes (after M1's fix) is correct.
- **`browser.storage.sync`** for cross-device config sync is the right choice.
- **TypeScript strict mode + `isolatedModules`.** Catches accidental cross-file leaks.
- **Tabs cleanup on close** (`background.ts:27-29`) — good housekeeping.
- **`ctx.isValid` guards** on every async callback in content.ts protect against extension reload/update mid-callback.
- **`window.postMessage(... , '*')` for content↔main-world.** Correct pattern for the isolated/main world boundary; the `*` target is fine since the message contains no secrets and the main-world script filters by `event.data?.type === 'link-scrubber-config'`.
